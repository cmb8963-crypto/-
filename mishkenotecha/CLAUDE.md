## 0. החלטות שהתקבלו עם המשתמש (גוברות על הסעיפים שאחריהן)

1. **שם וכתובת:** בממשק השם נכתב **"משכנותיך"**. הכתובת: `chaimbreuer.co.il/mishkenotecha`, בתיקייה `mishkenotecha/` במאגר של האתר הקיים.
2. **טכנולוגיה:** בונים כמו האתר הקיים, ולא לפי סעיף 3:
   - אתר סטטי (HTML, CSS ו-JavaScript רגיל, בלי bundler), שמוגש ב-GitHub Pages.
   - שרת: Google Apps Script, והנתונים בגיליון Google פרטי. אין עלויות שרת.
   - מודל הנתונים מסעיף 10 הוא **מודל לוגי**: כל model הוא גיליון, וכל שדה הוא עמודה. ערכים נשמרים כטקסט (`"true"`, `"2026-10-12"`). עמודות שמתחילות ב-`_` (סיסמאות) לא נשלחות לדפדפן אף פעם.
   - "טרנזקציה" = נעילת סקריפט, ואחריה `MK.run()` מחשב את כל השינויים, ורק אז הכול נכתב.
   - בדיקות: Vitest (`npm test`). Lint: ESLint (`npm run lint`). Build: `npm run build` (בונה את `apps-script/dist/Code.gs`).
3. **הפרדה:** המערכת נפרדת לגמרי מ-`/app` (המערכת הפרטית): פרויקט Apps Script נפרד, גיליון נפרד, משתמשים נפרדים.
4. **כניסה:** מייל וסיסמה. **לכל משתמש יש מייל וסיסמה משלו.** כרגע יש מנהל אחד שנוצר בעזרת קוד הגדרה חד-פעמי. ניהול משתמשים נוספים יגיע בשלב 5.
5. **עיצוב:** שפה עיצובית משלה (כחול-נייבי עמוק, פונט Heebo), שונה מהמערכת הפרטית.
6. **היקף ושינוי כיוון (אחרי סבב הדגמות עם המשתמש):** המערכת נבנתה מחדש סביב **יומן משימות אישי** ותיקים מפורטים. המודל הזה **גובר על סעיף 4.2**:
   - **ארבעה סוגי משימות:** שלי, מעקב אחרי אנשים (אחרי מי ומה הוא אמור לעשות), מעקב תיקים (משויך לתיק מהרשימה, עם "מי מטפל" שהוא אני או אדם אחר), וניהול ארגוני (מחלקה). יש לשונית "הכול" שמציגה את כל המשימות שלי.
   - **לכל משימה יש תאריך פתיחה** (`openedAt`). משימת המשך יורשת את תאריך הפתיחה, ונספר לה **סבב** (`steps`).
   - **סגירת משימה בתיק:** קודם מסמנים בוצע או לא בוצע, אחר כך כותבים פירוט, ובסוף בוחרים צעד הבא (מה, מי ומתי) או "אין צעד הבא כרגע". מעקב אחרי אדם נסגר ב"זה בוצע" או ב"עוד לא", ואז בוחרים מתי לבדוק שוב.
   - **בתיק יכולות להיות כמה משימות פתוחות.** הכלל "בדיוק משימה פתוחה אחת" בוטל. במקומו יש בדיקה לילית ששולחת מייל אם יש תיק פתוח בלי צעד הבא, בלי פרטי התיק.
   - **כרטיס תיק** לפי עמודות הגיליון של המשתמש: שם, נתונים חשובים, עיר, מפנה, מכיר את התיק / ראש חבורה, תאריך פנייה ראשונה, טלפון, הערות חשובות, סיפור התיק, ומצב (פתוח / בהמתנה / סגור עם סיבה).
   - **היסטוריה ועדכונים:** עדכונים חופשיים עם תאריך ושעה, משימות שהסתיימו (בוצע / לא בוצע, מי טיפל, פירוט), ומסמכים.
   - **מסמכים:** כל מסמך נשמר ב**גוגל דרייב**, בתיקייה נפרדת לכל תיק בתוך "תיקים - מסמכים". בגיליון נשמרים רק המזהה והקישור. אפשר לפתוח, להוריד או להסיר מסמך, וקובץ שהוסר עובר לסל האשפה של הדרייב. הגודל המקסימלי הוא 25MB.
   - תגיות ואנשי קשר מהגרסה הקודמת הוסרו בינתיים. מחזירים אותם רק אם המשתמש מבקש.
   - שלבים 2 עד 5 עדיין פתוחים.

### מיפוי מבנה התיקיות (במקום סעיף 11)
```
mishkenotecha/
  index.html              → אפליקציית עמוד אחד (ניתוב ב-hash: #/ ‏#/cases ‏#/case/<id>)
  css/app.css
  js/core.js              → כל הכללים והפעולות (MK.run): משימות, תיקים, עדכונים, מסמכים, תאריכים ותוויות
  js/api.js               → תקשורת + שרת הדגמה
  js/app.js, pages.js, dialogs.js, ui.js
  apps-script/src/Server.js → השרת: כניסה, גיליון, תיקיות וקבצים בדרייב, גיבוי לילי
  apps-script/build.sh    → dist/Code.gs = core.js + Server.js
  tests/                  → Vitest
```

### כללי עבודה (בנוסף לסעיף 12)
- כל כתיבה עוברת דרך `MK.run(op, db, input, ctx)` ב-`js/core.js`. הפונקציה לא משנה את ה-db, אלא מחזירה `changes` ו-`removed`, והשרת כותב את שניהם תחת נעילה. את `addDocument` מפעיל רק השרת, אחרי שהקובץ נשמר בדרייב.
- אסור לכתוב כלל עסקי בשרת או בממשק. כל כלל נכתב ב-core.js ונבדק שם.
- כל ערך שמוצג בממשק עובר escape (`UI.esc`). קישורים למסמכים חייבים להתחיל ב-`https://`.
- יומן הפעולות (audit) ומיילי ההתראה מכילים רק מזהים ושמות פעולות, אף פעם לא תוכן של תיקים.
- `no-console` מופעל ב-ESLint.

## 1. רקע ומטרה
מערכת ניהול פנימית עבור ארגון "משכנותך". הליבה היא ניהול תיקים (אברכים / פניות) בעזרת מנגנון משימות משורשר: אף תיק פעיל לא נשאר בלי "המשימה הבאה". לצד הליבה יש ניהול מדריכים, דיווח פגישות, שכר ותזרים, וניהול קורס מדריכים.

**משתמשים:** כרגע משתמש אחד (מנהל המערכת). בהמשך יתווספו משתמשים, לכן כבר עכשיו בונים מודל משתמשים ותפקידים, גם אם בפועל יש רק ADMIN.

## 2. עקרונות UX (מחייבים)
- **פשטות מעל הכול.** מינימום קליקים, מינימום שדות חובה, זרימת עבודה טבעית.
- **עברית ו-RTL מלא:** `<html lang="he" dir="rtl">`, כל הטקסטים בממשק בעברית, תאריכים בפורמט `dd/MM/yyyy`.
- **רספונסיבי:** עובד באותה איכות במחשב ובטלפון. בטלפון: כפתורים גדולים, טפסים בעמודה אחת.
- **מסך הבית = יומן המשימות של היום.** זה המסך הראשון שנפתח.
- **הוספה מהירה:** כפתור "+" קבוע (תיק חדש / משימה חדשה) שזמין מכל מסך.
- **אזור זמן:** `Asia/Jerusalem`. "היום" מחושב תמיד לפי שעון ישראל, לא UTC.
- **מקלדת:** Enter שולח טופס, Esc סוגר מודאל.
- **פידבק מיידי:** הודעת toast אחרי כל שמירה. בלי ריענון עמוד.

## 4. מודול ניהול תיקים (ליבת המערכת)

### 4.1 כרטיס תיק
| שדה | חובה | הערות |
|---|---|---|
| שם התיק / האברך | ✔ | |
| טלפון | | |
| עיר | | |
| גורם מפנה | | טקסט חופשי (גיס, מטפל, שכנים...) |
| מי מכיר את התיק / ראש חברה | | |
| תאריך פנייה ראשונה | | ברירת מחדל: היום |
| סיפור התיק | | טקסט ארוך: מה הסיפור, מה ידוע, מה עדיין לא ידוע |
| נושאי טיפול (תגיות) | | בחירה מרובה מתוך רשימה ניתנת לעריכה |
| סטטוס | ✔ | פעיל / בהמתנה / סגור. ברירת מחדל: פעיל |
| דחוף | | דגל בוליאני. תיק דחוף מוצג ראשון ביומן |
| משימה ראשונה + תאריך יעד | ✔ | נדרשת בעת פתיחת תיק חדש |

**תגיות התחלתיות (נטענות ב-seed, ניתנות לעריכה במסך הגדרות):**
ליווי ומעקב תיקים, ניהול תיקים מורכבים, מתווה לבית בפנים, קשר עם מטפלים, שאלות לקודש, שאלות הלכתיות לרבנים, פוריות, קביעת תורים לגורמי מקצוע.

**אנשי מקצוע:** שמות של אנשי מקצוע לא נשמרים כתגית אלא ברשימת אנשי קשר מקצועיים (מודל `Contact`), שאפשר לשייך למשימה.

### 4.2 מנגנון משימות ושרשור (Task Chaining). זה הכלל החשוב ביותר במערכת.
1. כל משימה כוללת תיאור ותאריך יעד, ושניהם חובה.
2. **סגירת משימה** פותחת מודאל בשני שלבים, באותו חלון:
   - **שלב א, דיווח ביצוע (חובה):** טקסט חופשי שמתעד עם מי דובר, מה נסגר ומה התקדם. אפשר גם לבחור איש קשר מהרשימה.
   - **שלב ב, מה הלאה (חובה):** שתי אפשרויות בלבד:
     - **משימה הבאה:** תיאור ותאריך יעד. ברירת המחדל לתאריך היא מחר, ויש כפתורי קיצור: מחר / עוד 3 ימים / שבוע הבא.
     - **סגירת התיק:** דורשת סיבת סגירה קצרה.
   - אין אפשרות לסגור את המודאל באמצע ולהשאיר משימה מסומנת כבוצעה בלי המשך. הכול נשמר בטרנזקציה אחת.
3. **אינווריאנט:** לכל תיק בסטטוס "פעיל" או "בהמתנה" יש בדיוק משימה פתוחה אחת בשרשרת הראשית. בדוק את זה ב-Server Action ובבדיקות.
4. משימה חדשה נשמרת עם `previousTaskId`, כך שנוצרת היסטוריה רציפה של התיק.
5. **דחיית משימה:** אפשר לשנות תאריך יעד בלי לסגור את המשימה, וכל דחייה נרשמת (`postponeCount`, תאריך מקורי).
6. **משימות כלליות:** משימות שלא שייכות לתיק (למשל משימות מחלקה או הקמת קורס). עליהן כלל השרשור לא חל.
7. **ציר זמן בכרטיס התיק:** רשימה כרונולוגית של כל המשימות שבוצעו, עם דיווחי הביצוע שלהן.

### 4.3 יומן משימות יומי (מסך הבית)
- מציג שלוש קבוצות, בסדר הזה:
  1. **באיחור:** תאריך יעד שכבר עבר. מודגש באדום.
  2. **להיום.**
  3. **קרוב:** 7 הימים הבאים. מקופל כברירת מחדל.
- בתוך כל קבוצה תיקים דחופים מופיעים קודם, ואחר כך המיון לפי תאריך.
- כל שורה כוללת שם תיק, משימה, תאריך יעד, תגיות, כפתור "בוצע" (שפותח את מודאל השרשור) וכפתור "דחה".
- לחיצה על שם התיק פותחת את כרטיס התיק.
- סינון לפי תגית, מחלקה, ותאריך או טווח תאריכים.

### 4.4 רשימת תיקים
טבלה עם חיפוש לפי שם או עיר, וסינון לפי סטטוס ותגית. לכל תיק מוצגת המשימה הבאה ותאריך היעד שלה.

## 5. מודול מדריכים, פגישות ושכר

### 5.1 חתנים
מודל נפרד `Groom`: שם, טלפון, מדריך משויך, תאריך חתונה, מחיר מוסכם, וסטטוס (בהדרכה / הסתיים).

### 5.2 מדריכים
- רשימה ראשונית ב-seed: שלושת המדריכים מהמסמך המקורי. בפועל מזינים אותם במסך, ולא בקוד, כי המאגר ציבורי.
- אפשר להוסיף מדריך, לערוך אותו או להשבית אותו. מדריך לא נמחק, כדי לשמור על ההיסטוריה.
- לכל מדריך שני תעריפים: תעריף לשעת הדרכה רגילה, ותעריף לפגישה שאחרי החתונה.

### 5.3 דיווח פגישות
- טופס מהיר: מדריך, חתן, תאריך, משך בשעות (ברירת מחדל 1), סימון "אחרי החתונה", הערה.
- **מכסה:** 15 פגישות לחתן כברירת מחדל, וניתן לשינוי ברמת החתן. בכרטיס החתן מוצג מונה, למשל "9 / 15".
- כשמדווחים פגישה מעבר למכסה, המערכת מציגה אזהרה (לא חסימה).
- פגישה שאחרי החתונה נספרת בנפרד ומתומחרת לפי התעריף השני.

### 5.4 חישוב שכר
- דוח חודשי לכל מדריך: מספר שעות רגילות כפול תעריף, ועוד פגישות אחרי חתונה כפול תעריף.
- אפשר "לנעול" חודש ששולם (`PayrollPeriod`). אחרי הנעילה אי אפשר לערוך פגישות של אותו חודש.

### 5.5 גבייה
- הארגון גובה ישירות מהחתנים, והמדריכים לא גובים.
- תשלומים נרשמים מול חתן (`Payment`). המערכת מציגה יתרה לגבייה: המחיר המוסכם פחות מה ששולם.

## 6. מודול כספים ותזרים
- תנועות: הכנסה או הוצאה; סיווג קבוע / משתנה / תקופתי; קטגוריה; מחלקה; סכום; תאריך; תיאור.
- **מחזוריות:** לתנועה קבועה אפשר להגדיר מחזור (יומי, שבועי, חודשי, דו-חודשי, תקופתי). המערכת מציגה תחזית תזרים קדימה על בסיס התנועות הקבועות.
- **דוחות:** סיכום לפי טווח (יום, שבוע, חודש, תקופה מותאמת), לפי קטגוריה ולפי מחלקה.
- חשבונות בנק: רשימת חשבונות והיתרה הידנית העדכנית בכל אחד.
- הנפקת חשבוניות וקבלות **לא נכללת בשלב הזה.** בעתיד: חיבור לשירות חיצוני כמו חשבונית ירוקה או iCount. ההנפקה עצמה לא נבנית בתוך המערכת.

## 7. מודול קורס מדריכים
- **לוח הקמה:** משימות כלליות שמשויכות לפרויקט "קורס מדריכים", עם אחראי, תאריך יעד וסטטוס. דוגמאות: שיחות תיאום עם המדריכים, קביעת מחיר וגבייה, תאריכים, מיקום, סילבוס, אישור תכנים, תיאום בין המדריכים.
- **ספריית תכנים (שלב מתקדם):** העלאת הקלטות, תמלולים ומסמכים. האחסון באחסון קבצים חיצוני (כאן: Google Drive), ובמסד הנתונים נשמר רק הקישור. הגישה פתוחה לתפקיד INSTRUCTOR בלבד, ולתפקיד הזה אין שום גישה לתיקים.

## 9. סדר הבנייה (שלבים)
**שלב 0: תשתית** ✔ *(נבנה)*

- כניסה עם משתמש ADMIN. כל המסכים מוגנים.
- seed: תגיות. (משתמש: נוצר בקוד הגדרה. מדריכים: בשלב 2, דרך המסך.)

**שלב 1: תיקים ומשימות (הליבה)** ✔ *(נבנה, ואחר כך הורחב לפי סעיף 0.6)*
- יצירת תיק עם משימה ראשונה, רשימת תיקים, כרטיס תיק עם ציר זמן.
- מודאל סגירת המשימה והשרשור (סעיף 4.2), כולל טרנזקציה ובדיקת האינווריאנט.
- דחיית משימה.
- יומן יומי (סעיף 4.3) כמסך הבית.
- בדיקות: כל לוגיקת השרשור והאינווריאנט מכוסה בבדיקות יחידה (Vitest).

**שלב 2: מדריכים, חתנים ופגישות**
- ניהול מדריכים וחתנים, דיווח פגישות, מונה מכסה, דוח שכר חודשי ונעילת חודש.

**שלב 3: גבייה וכספים**
- תשלומים מחתנים, תנועות, תנועות מחזוריות, דוחות ותחזית תזרים.

**שלב 4: קורס מדריכים**
- לוח ההקמה, ואחר כך ספריית התכנים והרשאות INSTRUCTOR.

**שלב 5: משתמשים נוספים**
- ניהול משתמשים ותפקידים (לכל משתמש מייל וסיסמה משלו), ושיוך משימות ותיקים לאחראי.

## 10. מודל הנתונים (גיליונות)
- `users`: id, name, email, role (ADMIN/STAFF/INSTRUCTOR), isActive, createdAt, `_salt`, `_passHash`, `_passVer` (העמודות המוסתרות לא נשלחות לדפדפן).
- `cases`: id, name, phone, city, info (נתונים חשובים), referredBy, knownBy, firstContact, notes, story, status (open/waiting/closed), closeReason, closedAt, folderId (תיקייה בדרייב), createdAt, updatedAt, createdBy.
- `tasks`: id, kind (mine/people/case/org), title, due, original, moved, lastMovedAt, who, what, caseId, owner, dept, done, result (done/notdone), note, completedAt, completedBy, openedAt, steps, prevId, createdAt, createdBy.
- `logs`: id, caseId, text, auto (שינוי אוטומטי), createdAt, by.
- `documents`: id, caseId, name, note, mime, size, fileId, url, createdAt, by.
- `audit`: רק מזהים ושמות פעולות.

## 12. כללי עבודה ל-Claude Code
- כל הטקסטים בממשק בעברית. שמות קוד, משתנים ו-enum באנגלית. התרגום לעברית מרוכז ב-`js/core.js`.
- כל פעולה שנוגעת ביותר מטבלה אחת מחושבת במלואה ב-`MK.run`, ונכתבת תחת נעילה.
- לוגיקת השרשור נמצאת רק ב-`js/core.js` ומכוסה בבדיקות.
- אין מחיקה פיזית של תיקים, מדריכים או חתנים. משתמשים בסטטוס או ב-`isActive` בלבד.
- כסף: בלי float. בממשק מציגים `₪` עם `Intl.NumberFormat('he-IL')`.
- לפני מעבר לשלב הבא: `npm run build`, `npm run lint` ו-`npm test` עוברים בלי שגיאות.
- המידע בתיקים רגיש: אין להדפיס אותו ל-console, ואין לכלול נתונים אמיתיים בקוד, בנתוני ההדגמה או בבדיקות.
- אם דרישה לא ברורה, עוצרים ושואלים. לא מנחשים.
